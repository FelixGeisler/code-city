= Deployment View

== Standalone application artifact

The repository produces one canonical manifest-bound application artifact in
`dist/`. It contains public browser UI, analysis worker and parser assets,
and a private native Node.js host with a bounded saved-data validator. The repository does not deploy that
service. The operator supplies `--port`; binding defaults to loopback.
Browser Web Crypto requires HTTPS or a secure localhost context. A remote TLS
ingress and its trust configuration are not provided by this milestone.

No device, Internet, authentication, direct private-provider, performance, concurrency,
or memory deployment claim is made. Raspberry Pi qualification remains
pending.

== Verification path

Pull-request CI performs locked install, dependency closure, high-severity
security audit, the isolated Node type check, and `npm run verify`. That root
gate first qualifies native folder access in isolated installed Chrome, then
runs type checking and tests, builds the canonical artifact once,
reproduces its manifest and every recorded byte in an isolated directory,
drives the actual packaged server/worker/parser/browser, verifies signal
shutdown, validates the immutable retirement evidence, and builds the docs. It
does not publish.

Linux native qualification additionally requires Python 3, Xvfb, libX11 and
libXtst (XTEST extension). These are test-machine dependencies, not packaged or
production runtime dependencies. Keyboard input is confined to the gate's own
verified Xvfb server and owned Chrome/chooser focus; it never uses the caller's
`DISPLAY`. Qualification still requires a real native directory handle, granted
read permission and successful acquisition, not merely completed UI actions.

The native qualification tool observes its own Chrome child's startup immediately
at launch, before asynchronous process metadata or helper inspection. Its CDP
endpoint deadline remains 20 seconds from registration. Early spawn errors and
exits (including already-terminal children) reject startup; an early rejection
remains available to the owner after setup without an unhandled rejection.
Startup settlement releases its listeners and timer. Failure console output
includes available owned-child startup/exit state and at most 16 KiB of stderr;
no profile upload or additional CI artifact is introduced. Endpoint acceptance,
PID/profile/display ownership checks and shutdown qualification remain unchanged.
A no-GUI Node regression demonstrates the lost-event race in the old waiter;
this does not establish the cause of a prior hosted timeout whose startup state
was unavailable.

=== Windows native isolation

The normal checker and `npm run verify` automatically launch the Windows native
stage on a fresh `WinSta0\\CodeCityNative-<nonce>` desktop. The observing parent
never enumerates or acts on windows. It creates the desktop without
`DESKTOP_SWITCHDESKTOP`, creates a non-breakaway kill-on-close job, and launches
Node suspended with explicit `STARTUPINFO.lpDesktop`. Before resuming it, the
parent assigns the job and records its own PID/creation time/executable and the
child's PID/creation time/executable/desktop in an ordinary nonce-bound Temp file.
Windows child-process desktop inheritance carries this desktop to Chrome and
PowerShell helpers; see
https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow[STARTUPINFOW].
No desktop switch, input-desktop fallback, global input, foreground API or
active-desktop window/content inspection is used.

A record/environment variable alone authorizes nothing. Before Chrome discovery
and again immediately before launch, an actual inherited no-GUI helper validates
its current desktop against the nonce, the query-only input-desktop identity,
live parent and Node launch identities, Node parentage and job membership.
Every helper invocation repeats those checks, including manual invocation of the
helper. Win32 action wrappers additionally validate the exact target window's
PID, job and thread desktop immediately before the native call. UIAutomation
focus and Invoke have the same immediate owned-window check. CDP picker/focus
actions require a uniquely identified isolated browser window first. A missing,
changed, input or unprovable identity fails before actuation. Non-USER Node
threads have no queryable desktop; their launch binding and the inherited
helper's actual USER desktop are the pre-browser proof, not a fabricated thread
query result.

The owner holds the desktop until job accounting proves *all* descendants have
exited, not merely recorded browser children. Failure terminates only the owned
job, remains failure, and joins it before closure. Cleanup closes child handles,
closes the desktop, proves that exact desktop absent through `EnumDesktops`,
closes/proves absence of the named job, then removes its metadata. An uncertain
observation retains the precise record and fails. The historical
`EnumDesktopWindows` finalization error remains a failed historical run; it is
not reinterpreted as an empty desktop. The new observer uses whole-job exit and
exact desktop-object absence instead of that failed window-count inference.
Fixture/profile ownership and cleanup checks remain mandatory in the checker.

Native shutdown requests `Browser.close` and joins the launch-time process plus
inherited-stdio close barrier within the existing 15-second deadline. A lost CDP
response alone must not interrupt graceful exit. Only exit code zero with no
signal can pass; timeout, abnormal exit or forced cleanup remains failure.
Evidence records the request outcome, close result and process/stderr state
before forced cleanup and at completion. The first shutdown error remains
primary; subsequent cleanup observations are recorded separately rather than
replacing it.

Windows cleanup opens the recorded PID and explicitly retains its process handle
before the first identity or liveness check; `GetProcessById` alone does not bind
that handle. Failure to bind fails closed. Creation time, `Process.HasExited`
and the recorded executable are checked before any signal. The same handle is
retained through termination so PID reuse cannot retarget it, and disposed on
every outcome. A process object can retain its creation time and handle after
exit; those are identity evidence, not liveness. No-GUI regressions check the
production predicate's initially unbound object and retained binding, refused
identities, unavailable binding, disposal, and actual children with exit code 259
(`STILL_ACTIVE`), a lost close response, and inherited stderr held by a descendant.
They reproduce these races but cannot identify the first close error in the
historical failed run, where a later remaining-process assertion overwrote it.

`node tools/check-local-folder-native.mjs --isolation-proof --evidence <directory>`
exercises only an owned no-GUI Node/helper child and the production guards. It
never starts Chrome or focuses a window. Regression tests compile the actual
Win32 wrappers and reject Default/wrong/input desktop identities before native
actuation, and exercise wrong owner creation/job identities and cleanup. This
establishes isolation plumbing, not native Chrome qualification. Real capability
and cleanup qualification requires a separately authorized isolated native probe;
no-GUI results alone are insufficient. Packaged/headless checks and the Linux
isolation path are unchanged.

Windows helper failures attempt to save their process/start-time and chooser/control
snapshot in `result.json` before propagating the original nonzero helper error.
Snapshots record their time, phase, desktop name, chooser PID/visibility,
permission control enabled/offscreen/focus state, and owned-window GUI-thread
activation on the validated non-input desktop. No input-desktop foreground
information or other window's identity, title or content is collected. Permission
actions also record the invoked runtime ID, invocation times and a fresh
post-action prompt snapshot. A picker-resolution timeout also
captures the remaining owned browser prompt and picker state, without sending
another action or extending the deadline. If either failure-diagnostic save fails,
the original error remains primary; the secondary save error is reported on stderr
as not persisted and retained in memory (one message of at most 2,048 characters
per failure path) for any later normal flush. No save retry is added; normal saves
and final cleanup/error handling remain mandatory and unchanged.
These are diagnostics, not proof that a completed button invocation granted read
access. A synthetic reproduction retained the same enabled prompt after Invoke
even with foreground and button focus proved immediately before the call.

Windows permission interaction therefore separates focus acquisition from
Invoke. It focuses the verified owned permission button once, then observes the
same enabled, visible, focused target, unchanged bounds and per-desktop active
owned window for Windows' `GetDoubleClickTime()` interval. The old global
foreground assumption is not applicable to a non-input desktop; this replacement
is conditional on validated isolation and still needs real capability acceptance. Chromium uses this interval
for dialog input protection; its accessibility Invoke can return success without
acceptance. See the qualifying browser revision's
https://github.com/chromium/chromium/blob/fb096c0011f9d50f0a264a9376420cdea9c421e3/chrome/browser/ui/file_system_access/file_system_access_permission_dialog.cc[permission dialog],
https://github.com/chromium/chromium/blob/fb096c0011f9d50f0a264a9376420cdea9c421e3/ui/views/input_event_activation_protector.cc[input protector], and
https://github.com/chromium/chromium/blob/fb096c0011f9d50f0a264a9376420cdea9c421e3/ui/views/metrics_aura.cc[Windows interval].
Loss of focus, movement or identity change fails without restarting the interval
or repeating input. One Invoke follows readiness; actual picker resolution,
granted native permission and acquisition remain mandatory. The 20-second helper
and 10-second resolution bounds are unchanged. Offscreen placement is not an
isolation boundary and is no longer used. GUI interaction is permitted only
within the newly owned non-input desktop; never on the user's active desktop.

The observed focus/acceptance timing supports this readiness repair, but the
browser's internal rejection branch was not instrumented. Exact attribution of
earlier unresolved-picker runs remains uncertain; the separate inspect/select
cardinality failure is not explained by this change. The old isolated-desktop
observer's error is replaced by the cleanup protocol above, not explained away. Successful synthetic runs do not retrospectively prove
all historical failures repaired.

== Main publication path

A protected-main push repeats the same gates and creates a publication record
bound to `dist/package-manifest.json`, the exact commit, and the workflow run.
It uploads the exact audited `dist/` directory as the standalone artifact and
uploads the manifest plus publication record as internal identity evidence.
No Pages upload or deployment action, Pages or ID-token write permission,
`github-pages` environment, eligibility query, or hosted analyzer observation
job remains.

== Completed retirement cleanup

`publication/retirement-live-verification-v1.json` records the exact #625 merge
commit and successful automatic Publish run, every uploaded artifact ID and
downloaded ZIP SHA-256, equality of the uploaded standalone manifest and its
publication-record binding, exact live root and `/index.html` notice bytes, and
`404` responses for all eight URLs in
`publication/former-analyzer-assets-v1.json`. Its request and checkout
timestamps establish that the live gate completed before cleanup editing.

The cleanup removed repository workflow deployment capability and the obsolete
hosted-analyzer observer only after that gate passed. The last script-free
notice may remain reachable. This repository makes no claim that the GitHub
Pages repository setting was disabled, deleted, or changed.

== Saved data and later deployment

`--data-dir` selects a dedicated local directory outside the artifact. Snapshot
files survive artifact replacement and host restart. The operator, not the
builder or publication job, owns backup/deletion/recovery; see
xref:requirements:saved-investigations.adoc[Saved Investigations].
Release hosting, TLS ingress, device operation and private providers remain
unselected. Login and accounts are not required by the shared-view product.
