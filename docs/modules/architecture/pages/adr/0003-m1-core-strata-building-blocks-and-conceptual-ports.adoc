= ADR 0003: M1 core strata, building blocks, and conceptual ports

Status:: Accepted

== Context

xref:adr/0001-core-dependency-boundary.adoc[ADR 0001] establishes one conceptual
core and one collective edge/adapters side, permits source dependencies from
edge/adapters to core, and forbids source dependencies from core to
edge/adapters. It deliberately leaves the core's internal structure and the
minimum building blocks and conceptual ports to
https://github.com/FelixGeisler/code-city/issues/462[#462].

xref:adr/0002-browser-only-runtime-and-github-pages-deployment.adoc[ADR 0002]
places UI application and presentation work in the browser main context and
processing application, provider, parser, and city work in at most one
same-origin dedicated processing worker. Placement does not establish source
layers or dependency directions.

M1 needs a minimum assignment of orchestration, deterministic policy, provider
and parser translation, presentation adaptation, state, failure, admission,
cancellation, and cleanup responsibilities. Without that assignment, the
implementation slices could create competing orchestration or admission paths,
leak edge-specific values into core policy, or establish an accidental source
architecture.

This ADR refines ADR 0001's core into application and domain strata and fixes
minimum logical responsibilities and conceptual port roles under ADR 0002's
placement. It does not supersede either ADR, and both remain unchanged. ADR
0001 remains authoritative for the outer core/edge source boundary, and ADR
0002 remains authoritative for runtime and deployment placement.

== Decision

=== Core strata and edge

The conceptual core has two source-dependency strata:

. *Application core:* current-attempt and worker-stage orchestration and
  ownership of application driving and driven ports.
. *Domain core:* canonical values and pure deterministic input, state,
  identity, admission, metric, and city policies.

Provider, UI/shell, UI-worker bridge, parser, and renderer mechanisms are
*edge/adapters*. These are responsibility boundaries, not packages,
components, execution contexts, or deployment nodes.

The capability-scoped cross-stratum source graph is:

[source,text]
----
edge/adapters ----------------> application core ----> domain core
       +-----------------------------------------------> domain core
----

The cross-stratum source-dependency whitelist is exactly these three arrows:

* `edge/adapters → application core`;
* `edge/adapters → domain core`, only under the capability constraint below;
  and
* `application core → domain core`.

This ADR does not decide the general same-stratum source graph or concrete
source mapping. Within the application stratum,
`worker-pipeline application coordination → named worker-stage application capabilities`
is expressly permitted. The ownership and bypass prohibitions below remain
mandatory.

The following source dependencies are forbidden:

* `domain core → application core`;
* `domain core → edge/adapters`;
* `application core → edge/adapters`;
* UI application → worker-pipeline implementation or the reverse; and
* a stage capability → a predecessor stage's implementation.

Analysis consumes admitted-module contracts, not retrieval implementation.
City construction consumes canonical metric contracts, not analyzer
implementation.

Direct `edge/adapters → domain core` access is permission only for implementing
a core-owned port or adapting canonical domain values. Production actions still
enter through application driving ports. An adapter must not create a second
orchestrator, admission path, metric path, or city-construction path. Port
contracts remain with their application or domain semantic owner; there is no
separate contracts layer. This ADR does not revive ADR 0001's former blanket
adapter/domain or framework/storage classifications.

=== Meanings kept distinct

* A *source-dependency arrow* means source on the left may import or otherwise
  depend on source on the right.
* A *runtime flow* may call an outward adapter through a core-owned driven port
  and receive data inward without reversing the source dependency.
* *Runtime messages* may move both ways between the UI and worker bridge
  halves. They grant no source dependency and create no trust crossing.
* *Placement* follows ADR 0002: UI application and presentation run in the
  main context, while processing application, provider, parser, and city work
  run in the worker. Placement does not define layering.
* *Driving* and *driven* labels define conceptual port roles only. They do not
  require an interface, package, or one-component-per-port design.

The bridge may carry only:

* toward the worker: one normalized, syntactically accepted submission and
  lifecycle control; and
* toward the UI: selected identity, one terminal failure, or one complete
  canonical scene.

Raw or normalized repository source or content, admitted modules, parser
objects, metric intermediates, and partial scenes must not cross. Building
identities may cross only as inert model keys. Exact message and port schemas
remain with #453 through #460.

=== Sole state, failure, admission, cancellation, and cleanup ownership

* *Visible state and publication:* the UI attempt coordinator only; the UI
  surface only displays it.
* *Input failure:* domain validation policy classifies it; the UI coordinator
  commits `Failure` before worker dispatch.
* *Resolution outcomes:* the revision-resolution capability.
* *Admission and RA outcomes:* the retrieval/admission capability only; no
  other block creates or readmits admitted modules.
* *Metric failure:* the static-metrics capability.
* *Construction failure:* the city constructor.
* *Presentation failure:* the presentation adapter detects it and cleans its
  resources; the UI coordinator alone commits visible `Failure`.
* *Worker sequencing and suppression:* the worker pipeline coordinator only.
* *Bridge behavior:* transport outcomes unchanged; never validate, classify,
  admit, or reclassify them.

On a worker-stage failure, the owning capability returns its terminal outcome,
the pipeline suppresses later stages and releases core transients, and the UI
applies the outcome only if that attempt remains publication-eligible.

Cancellation and cleanup are partitioned exactly once:

. The UI coordinator immediately revokes publication eligibility, wins ties,
  and clears identity, city, and presentation state while preserving the draft
  required by #441.
. The worker pipeline coordinates feasible stopping, suppresses downstream
  stages, and releases core transient references.
. Each provider or parser adapter releases only the physical resources it
  owns.
. The bridge releases transport references.
. The presentation adapter disposes incomplete or replaced presentation
  resources.

Late output is harmless because the UI publication gate remains authoritative.
Reload discards all application-managed session state. This decision adds no
cleanup-latency, secure-erasure, platform-cache, or garbage-collection promise.

== Rationale

The split makes mutable orchestration distinct from deterministic policy,
preserves provider, parser, and renderer independence and pure city
construction, gives #452 objective cross-stratum and named same-stratum
conformance rules, and supports focused #453 through #458 slices without
turning each slice into an architecture layer.

== Downside

The additional stratum and boundary translations add structural cost.
Capability-scoped edge-to-domain access creates bypass risk, so production
entry, sole admission, and publication ownership require behavioral evidence
as well as source-graph evidence.

== Rejected alternatives

* *Undifferentiated core.* It uses fewer concepts but leaves the separation of
  policy and orchestration convention-only and not objectively protectable.
* *Adapters may depend only on application.* It creates a stronger funnel but
  adds unsupported wrappers or duplicate translations for canonical
  identities, syntax, and scenes.
* *Blanket adapter-to-domain access.* It permits orchestration and invariant
  bypass.
* *Treat the three-arrow cross-stratum whitelist as a complete same-stratum
  policy.* It creates unsupported source-layout constraints.
* *Add a contracts layer, per-stage hexagons or packages, generic buses,
  registries, or extension abstractions.* No accepted M1 need supports them.

== Exclusions

This ADR does not select or change:

* product behavior or a requirements contract;
* a package or source layout, concrete source map, general same-stratum policy
  beyond the named permission and prohibitions, module name, executable
  interface, signature, DTO, message or port schema, or separate contracts
  layer;
* shell, framework, build, packaging, Pages workflow or route,
  endpoint/request/redirect/retry/retrieval, parser, analyzer, renderer,
  transport/worker/cancellation, test, dependency, enforcement-tool, or
  deployment technology;
* a threshold, limit, failure category, credential, persistence or storage
  port, cache, backend, additional runtime context, platform cleanup or erasure
  promise, compatibility commitment, future port, plugin, registry, generic
  bus, extension point, or per-stage hexagon; or
* an outcome owned by #447 through #460 or #463, a v1 behavior, or a v1
  implementation choice.
