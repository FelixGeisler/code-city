= Source Admission and Repository Limits

This page is normative for M1 source admission and the approved repository and
intake limits RA-01 through RA-09. It applies after the current attempt has
selected the immutable repository identity defined by
xref:04-functional-requirements.adoc#immutable-revision[]. Repository metadata,
paths, and source remain untrusted data.

The rules below define observable classification. They do not select a
retrieval or buffering mechanism, topology, process, component, port, parser,
renderer, clock, cancellation mechanism, safeguard location, enforcement
owner, or cleanup owner.

[[admission-terms]]
== Terms

Raw repository entry:: One opaque entry record reported for the selected
commit. A repository-root placeholder is not an entry.

Canonical path:: A structurally valid raw path after the segment-wise NFC
normalization in <<canonical-paths,M1-ADM-1>>. Structural validity is separate
from the RA-02 path-length and RA-03 depth limits.

Eligible source candidate:: An entry outside a submodule boundary whose
canonical path is within RA-02 and RA-03 and has one of the eight allowed
extensions. Candidate classification occurs before kind or content admission.

Normalized content:: A candidate regular file's content after the exact
transformation in <<content-normalization,M1-ADM-4>>.

Admitted module:: A candidate that is a regular file and has valid normalized
content. Its canonical module identity is its canonical path.

Byte:: One octet. Every byte maximum is an exact integer count.

[[untrusted-source]]
== M1-ADM-0: Untrusted source invariant

Repository metadata, paths, entry content, and source text are untrusted data.
Admission must never execute, evaluate, import, dynamically load, or otherwise
run any of them. A filename, media-type or binary claim, executable bit,
generated/vendor label, or claimed count or size cannot override this
contract. Admission does not parse syntax or test executability.

[[canonical-paths]]
== M1-ADM-1: Canonical paths and module identity

A raw path must be a non-empty sequence of Unicode scalar values and a
repository-relative sequence of non-empty `/`-separated segments. All of these
rules apply:

. A path beginning with `/`, a drive prefix such as `C:/`, or a UNC prefix such
  as `//server/` or `\\server\` is invalid.
. `/` is the only separator. A backslash is invalid and is never changed to
  `/`.
. Repeated or trailing separators and `.` or `..` segments are invalid.
  Separators and segments are never removed, inserted, collapsed, or resolved.
. C0 and C1 controls are invalid: `U+0000` through `U+001F`, `U+007F`, and
  `U+0080` through `U+009F`.
. Normalize each segment to Unicode Normalization Form C (NFC), then rejoin the
  segments with `/`.
. Perform no other path transformation. Preserve letter case, spaces,
  punctuation, extension spelling, and generated or vendor path segments.

A malformed representation that is not a sequence of Unicode scalar values is
invalid; it is not repaired. Invalid path data produces `Source admission
failed` with code `M1-ADM-1`.

Structural validity does not include limit compliance. After NFC, RA-02 counts
the complete canonical path's UTF-8 octets, including `/`, and RA-03 counts its
segments. A structurally valid path above either maximum produces
`Repository/admission limit exceeded` with the applicable RA code, not an
admission failure. No identity is admitted from an above-limit path.

The canonical module identity is exactly the canonical path. Exact duplicate
raw paths and distinct raw paths that normalize to the same NFC path collide.
A collision fails the whole attempt with `Source admission failed` and code
`M1-ADM-1`; no entry wins. Case-only paths remain distinct.

[[extension-allow-list]]
== M1-ADM-2: Closed extension allow-list

Only these final-segment extensions are eligible:

[source,text]
----
.js  .jsx  .mjs  .cjs  .ts  .tsx  .mts  .cts
----

The extension is the suffix beginning at the final `.` in the final path
segment. A final segment `.ts` and a compound name such as `name.d.ts` are
therefore eligible. Compare only the suffix's ASCII letters
case-insensitively, while preserving the complete canonical path's spelling and
case. No Unicode case mapping is used. No other extension or compound format
is inferred. Unsupported extensions and framework-specific formats such as
`.vue` are skipped.

[[entry-kinds]]
== M1-ADM-3: Entry kinds and submodule boundaries

Only a regular file can be admitted. An ordinary directory is skipped, even
when its name ends in an allowed extension. Every symbolic link is skipped
without interpreting or following its target, including an in-repository,
absolute, escaping, or dangling target. A submodule entry and every reported
descendant beneath its canonical path are skipped. Submodule content is not
part of the selected repository's admitted module set.

Missing, unknown, contradictory, or malformed kind data required to classify
an in-horizon entry fails the attempt with `Source admission failed` and code
`M1-ADM-3`. The regular-file executable bit and generated/vendor metadata do
not affect admission.

[[content-normalization]]
== M1-ADM-4: Content validity and normalization

For each candidate regular file, transform the complete raw content exactly
once in this order:

. Decode the complete octet sequence as strict UTF-8. Ill-formed UTF-8 fails
  with `Source admission failed` and code `M1-ADM-4`.
. Remove exactly one leading `U+FEFF` byte-order mark when present. A second
  leading or an interior `U+FEFF` remains source text.
. Reject content containing `U+0000` with `Source admission failed` and code
  `M1-ADM-4`.
. Replace each CRLF pair (`U+000D U+000A`) with LF (`U+000A`), then replace
  each remaining CR with LF.
. Perform no other transformation. Do not normalize Unicode, trim whitespace,
  add or remove a final newline, decode escapes, or rewrite source.

The resulting scalar-value sequence encoded as UTF-8 is the normalized
content. Empty content and valid non-ASCII text are valid. An untrusted binary
or media label cannot override the bytes, and no other binary heuristic
applies.

Executable, declaration-only, comments-only, empty, otherwise non-executable,
and syntactically malformed source text is admitted when its path, kind, and
content are valid. Downstream syntax and metric behavior are defined only by
xref:08-fixed-metric-semantics.adoc[]. Repository data is never run.

[[admission-composition]]
== M1-ADM-5: Bounded classification, collision handling, and order

Provider response order is not classification order. Admission uses these
finite conceptual horizons. They define observable results, not a buffering,
traversal, component, or enforcement design.

. *Entry horizon:* Observe at most `10,001` opaque entry records. The
  `10,001`st record establishes RA-01 and closes the attempt without inspecting
  record fields. Otherwise all records, at most `10,000`, enter the path
  horizon.
. *Path horizon:* Classify every bounded path through its first structural
  invalidity or the point where RA-02 or RA-03 excess is irrevocably
  established. An unread suffix beyond a path cutoff establishes no later
  fact. A structural path failure established in this horizon wins over path
  limit facts. Simultaneous path limits use ascending RA ID.
. *Metadata horizon:* Only if every path passes, compare complete canonical
  paths for collisions, identify submodule boundaries, apply extension and
  kind rules, and count RA-06. A collision (`M1-ADM-1`) governs over a
  kind-data failure (`M1-ADM-3`), and either governs over RA-06. A terminal
  metadata result prevents content inspection.
. *Content horizon:* Only if metadata passes, inspect candidate regular-file
  content in canonical identity order. Inspect no more than RA-04 plus one
  actual octet for one candidate and RA-05 plus one actual octet in aggregate.
  After an RA-04 cutoff, exclude that content's unread suffix; consider later
  identities only while the RA-05 horizon remains open. A content failure
  established from complete in-horizon content (`M1-ADM-4`) governs over an
  established RA fact. Simultaneous RA facts use ascending ID. Data beyond a
  raw cutoff is not inspected merely to seek another result.
. *Complete-set horizon:* Only when the content horizon completes without a
  raw cutoff, establish RA-07 through RA-09, then the no-module condition, then
  the complete ordered admitted set.

A `fail` is terminal for the whole attempt and publishes no admitted set. A
`skip` excludes only that entry. An `admit` adds one module unless another fact
fails the attempt. The first result discovered in provider order is never
implicitly the winner.

Sort successful module identities lexicographically by their unsigned UTF-8
octets. When one byte sequence is a prefix of another, the shorter sorts first.
Provider response, traversal, filesystem, and locale order cannot affect the
admitted set, order, collision result, or diagnostic.

[[limit-rule]]
== M1-LIM-0: Inclusive repository and intake limits

RA-01 through RA-09 are separate, non-configurable inclusive maxima. A value
below or exactly at its maximum continues without a separate visible result.
One unit above fails with category `Repository/admission limit exceeded` and
the winning RA code. Compliance comes from actual bounded contract data, never
a provider or repository claim.

[cols="1,3,2,6",options="header"]
|===
|ID |Dimension |Inclusive maximum |Exact counting and normalization semantics

|RA-01
|Repository entries inspected
|`10,000 entries`
|Count every raw entry record once before path or content normalization,
including files, directories, symlinks, submodules, reported submodule
descendants, unsupported names, and duplicates. Repeated records count again.
Exclude only a repository-root placeholder.

|RA-02
|Canonical path length
|`1,024 UTF-8 bytes per path`
|After structural validation and segment-wise NFC, encode the complete
canonical path including `/` separators as UTF-8 and count its octets once,
before extension admission. Exclude raw spelling and content.

|RA-03
|Path depth
|`64 segments per path`
|After structural validation and NFC, count non-empty `/`-separated canonical
segments. A root-level file has depth one; repeated segment text counts at each
occurrence. Measure before extension admission.

|RA-04
|One inspected entry's content
|`4,194,304 raw bytes`
|Count the actual raw octets of each candidate regular file whose content is
inspected, once before UTF-8 decode, BOM removal, or newline normalization.
Repeated reads do not add bytes; identical content at distinct paths counts
separately. Skipped kinds and unsupported paths contribute no content.

|RA-05
|Cumulative inspected content
|`52,428,800 raw bytes`
|Sum RA-04 once per inspected canonical entry in the current attempt. Equal or
shared content at distinct paths counts once per path. Exclude metadata, paths,
skipped-entry content, and repeated reads. Measure before content
normalization.

|RA-06
|Eligible candidates
|`5,000 candidates`
|Count each structurally valid, in-limit, allowed-extension entry outside a
submodule boundary once after path normalization and before kind or content
admission. Allowed-extension directories and symlinks count and are then
skipped. A repeated candidate counts again and can also establish a collision.

|RA-07
|Admitted modules
|`4,000 modules`
|Count each unique regular candidate with valid normalized content once after
admission and before sorting. Exclude skipped entries. Distinct identities with
identical content count separately; collisions admit none.

|RA-08
|Normalized content per module
|`2,097,152 UTF-8 bytes`
|Count one module's UTF-8 octets after the approved BOM removal and newline
normalization. Exclude raw bytes, identity bytes, and downstream data. Repeated
downstream consumption does not add bytes.

|RA-09
|Aggregate normalized admitted content
|`41,943,040 UTF-8 bytes`
|Sum RA-08 once for every admitted identity after normalization and before
downstream processing. Equal or shared text under distinct identities counts
once per identity; repeated consumption adds nothing.
|===

[[metadata-policy]]
== M1-LIM-1: Actual-data and missing-data policy

Absent, malformed, negative, contradictory, overflowing, or otherwise
untrusted count, size, or encoding claims neither prove compliance nor create a
limit failure. Actual records and octets are measured without arithmetic wrap.
A claim above a maximum is not enough to fail, and a claim at or below a
maximum is not enough to pass.

Missing essential in-horizon path data is `Source admission failed` with code
`M1-ADM-1`; missing essential kind data uses `M1-ADM-3`; and missing candidate
content uses `M1-ADM-4`. Explicit zero-octet content is valid. Data
intentionally outside a closed horizon is not reclassified as missing.
Symlink-target content and content beneath a known submodule are not required
and cannot make those skipped entries admissible.

[[outcome-precedence]]
== M1-OUT-2: Deterministic precedence

Only facts established inside the bounded horizons can compete. A cutoff closes
its horizon; opaque fields, unread suffixes, later identities beyond the
aggregate content cutoff, and downstream data are not inspected merely to seek
a different result.

Within those horizons:

. The `10,001`st opaque record establishes RA-01 without field inspection.
. In the path horizon, an established structural path failure (`M1-ADM-1`)
  governs over RA-02 or RA-03. Simultaneous path limits use ascending RA ID.
. In the metadata horizon, a collision (`M1-ADM-1`) governs over a kind-data
  failure (`M1-ADM-3`), and either governs over RA-06.
. In the content horizon, a content failure established from complete
  in-horizon content (`M1-ADM-4`) governs over an established RA fact.
. Across established admission facts, `Source admission failed` governs over a
  repository/admission limit result; simultaneous RA violations use ascending
  ID; `No supported modules` follows both.

Only the winning category and code are visible. Provider response, discovery,
traversal, and filesystem order cannot change them.

[[failure-invariants]]
== M1-OUT-3: Identity retention and atomic publication

Apply the state contract from
xref:04-functional-requirements.adoc#states[Observable states and transitions]
unchanged:

* replacement immediately invalidates the prior attempt, identity, status,
  city, and partial work;
* cancellation while Loading makes the attempt permanently ineligible to
  publish and clears its selected identity;
* every post-selection failure retains only the current canonical repository
  URL and full lowercase commit ID;
* no failure publishes an admitted set, metric result, city/scene model,
  partial city, stale city, or late result; and
* success publishes one complete city atomically with its current identity.

A late result from a replaced or cancelled attempt has no observable effect.
