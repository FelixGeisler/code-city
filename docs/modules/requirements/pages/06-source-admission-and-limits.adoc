= Source Admission and Resource Limits

This page is normative for the M1 source-admission and resource-limit contract.
It applies only after the current attempt has selected the immutable repository
identity defined by xref:04-functional-requirements.adoc#immutable-revision[].
It defines product data and observable stages, not a process, component, port,
API, parser, renderer, thread, device, or enforcement owner.

The choices on this page are a product-contract proposal. They become part of
the accepted M1 baseline only when a human explicitly approves the exact
revision that contains them. A passing build or automated review is not that
approval.

[[admission-terms]]
== Terms

Raw repository entry:: One reported entry at the selected commit, consisting
of its raw repository-relative path, entry kind, and content octets when this
contract requires content. A repository root placeholder is not an entry.

Canonical path:: A structurally valid raw path after the path normalization in
<<canonical-paths,M1-ADM-1>>. Structural validity is independent of the RA-02
path-length and RA-03 depth ceilings.

Eligible source candidate:: An entry outside a submodule boundary whose
canonical path has passed RA-02 and RA-03 and has one of the eight allowed
extensions. This classification is made before its entry kind or content can
admit or skip it.

Normalized content:: A candidate regular file's content after the exact
transformation in <<content-normalization,M1-ADM-4>>.

Admitted module:: A candidate that is a regular file and has valid normalized
content. Its canonical module identity is its canonical path.

Contract stage:: One of retrieval, admission, static processing, city
construction, or presentation as delimited in <<measurement-stages>>. A stage
is an observable product interval, not an architecture boundary.

City unit:: The renderer-independent coordinate unit supplied by the city
contract. This page limits measured coordinates but does not choose how source
or metrics map to them.

Byte:: One octet. Every byte threshold below is an exact integer count, not an
approximation.

[[untrusted-source]]
== M1-ADM-0: Untrusted source invariant

Repository metadata, paths, entry content, and source text are untrusted data.
Admission must never execute, evaluate, import, dynamically load, or otherwise
run any of them. A filename, media-type claim, executable bit, generated/vendor
label, or claimed count or size has no authority to override this contract.
Static processing may inspect normalized source under its accepted contract,
but it must not execute the source.

[[canonical-paths]]
== M1-ADM-1: Canonical paths and module identity

A raw path must be a sequence of Unicode scalar values. It is structurally
valid only when all of the following hold:

. It is non-empty and repository-relative.
. It does not begin with `/`, a drive prefix such as `C:/`, or a UNC prefix
  such as `//server/` or `\\server\`.
. It contains `/` as its only separator. A backslash is invalid and is never
  changed to `/`.
. Splitting on `/` produces only non-empty segments. No segment is `.` or
  `..`; separators are never removed, inserted, collapsed, or resolved.
. It contains no C0 or C1 control character: `U+0000` through `U+001F`,
  `U+007F`, or `U+0080` through `U+009F`.
. Each segment is normalized to Unicode Normalization Form C (NFC), and the
  segments are rejoined with one `/`.

All other Unicode scalar values are allowed. NFC is the only path text
normalization. Letter case, spaces, punctuation, and extension spelling are
preserved. In particular, no locale-sensitive or Unicode case folding is
performed.

Structural validity does not include resource-limit compliance. After NFC,
RA-02 measures canonical-path UTF-8 bytes and RA-03 measures canonical depth.
A structurally valid path with `1,025` bytes or `65` segments therefore produces
the applicable `Repository/admission limit exceeded` fact, not `Source
admission failed`. If both facts are established, RA-02 wins by ascending ID.
No module identity is admitted from an above-threshold path.

The canonical module identity of an admitted module is exactly its canonical
path. Generated and vendor path segments have no special meaning and are not
excluded.

Collision assessment occurs only after the bounded entry and path horizons in
<<admission-composition>> pass. At that point two complete canonical paths
collide when they are equal, including when the raw paths are exact duplicates
or distinct canonically equivalent Unicode strings. A collision is a `Source
admission failed` outcome for the whole attempt; no entry wins. ASCII case-only
variants do not collide because case is preserved. These are all possible
collision classes because NFC is the only identity-changing path operation.
A path suffix outside a terminal RA horizon is not inspected merely to seek a
collision.

[[extension-allow-list]]
== M1-ADM-2: Closed extension allow-list

Only these final-segment extensions are eligible:

[source,text]
----
.js  .jsx  .mjs  .cjs  .ts  .tsx  .mts  .cts
----

The extension is the suffix beginning at the final `.` in the final path
segment. The segment `.ts` therefore has the allowed `.ts` extension, and
`name.d.ts` has the allowed `.ts` extension. Eligibility compares only ASCII
letters in the suffix case-insensitively, so `.TS` and `.TsX` are eligible.
The canonical path and module identity retain their original case. No other
extension or compound format is inferred, and no Unicode case mapping is used.

[[entry-kinds]]
== M1-ADM-3: Entry kinds and submodule boundaries

Only a regular file can be admitted. An ordinary directory/tree entry is
skipped, even when its name ends in an allowed extension. Every symbolic link
is skipped without interpreting or following its target; this includes an
in-repository target, an absolute or escaping target, and a dangling target.
A submodule entry and every reported entry beneath its canonical path prefix
are skipped. Submodule content is not part of the selected repository's
admitted module set.

A missing, unknown, contradictory, or malformed entry kind is not silently
skipped; it is `Source admission failed`. The regular-file executable bit and
other mode metadata do not affect admission.

[[content-normalization]]
== M1-ADM-4: Content validity and normalization

The raw content of each candidate regular file is transformed exactly once in
this order:

. Decode the complete octet sequence as strict UTF-8. An ill-formed sequence is
  `Source admission failed`.
. Remove exactly one leading `U+FEFF` byte-order mark when present. An interior
  `U+FEFF`, or a second leading one, remains source text.
. Reject content containing `U+0000` with `Source admission failed`.
. Replace every CRLF pair (`U+000D U+000A`) with LF (`U+000A`), then replace
  every remaining CR with LF.
. Perform no other transformation: do not normalize Unicode, trim whitespace,
  add or remove a final newline, decode escapes, or rewrite source.
. Encode the resulting scalar-value sequence as UTF-8. Those octets are the
  normalized content counted by the normalized-content limits.

Empty content and valid non-ASCII text are admissible. For M1, content is
binary precisely when it is not strict UTF-8 or contains `U+0000`; there is no
filename, media-type, printable-character, or other binary heuristic. An
untrusted `binary` label cannot reject otherwise valid content or admit invalid
content.

Admission does not parse language syntax or decide whether code is executable.
Executable source, declaration-only source such as `name.d.ts`, comments-only
source, and otherwise non-executable source are all admitted. Syntactically
malformed source with otherwise valid path and content is admitted first, then
produces `Source processing failed` when fixed static processing evaluates it;
it is never reclassified or silently skipped by admission.

[[admission-composition]]
== M1-ADM-5: Composition, collision handling, and order

The closed matrix in <<admission-matrix>> uses this composition rule. Each row
assumes all conditions not stated in that row match the admissible baseline:
a unique regular file at `src/example.ts`, valid UTF-8 content `export {};`
with LF newlines, and every limit below its threshold.

Provider delivery order is not classification order. Admission uses these
finite conceptual horizons; they define product classification without
selecting a buffering, retrieval, or enforcement mechanism:

. *Entry-count horizon:* establish whether the repository-entry sequence is
  complete within RA-01 by observing at most `10,001` opaque entry records. If
  the `10,001`st record exists, RA-01 is the terminal result and entry fields
  are not classified. Otherwise, at most `10,000` records enter the next
  horizon. A permutation cannot change this count.
. *Path horizon:* for every record inside the entry-count horizon, inspect each
  path only through the first structural-invalid condition or the point at
  which RA-02 or RA-03 excess is irrevocably established. Continue this bounded
  path classification for every record. A structural path failure established
  inside the horizon wins over established path-limit facts; otherwise
  simultaneous path limits use ascending ID. A suffix beyond an individual
  path cutoff is not inspected and supplies no later structural or collision
  fact.
. *Complete-metadata horizon:* only when every path passes RA-02 and RA-03,
  compare all complete canonical paths for collisions, identify submodule
  boundaries, apply the extension and entry-kind rules, and count RA-06. This
  horizon contains at most `10,000` paths of at most `1,024` bytes and `64`
  segments each. Established essential-data or collision failures win over
  RA-06. If this horizon has a terminal result, no content horizon starts.
. *Content horizon:* only when metadata passes and RA-06 permits at most
  `5,000` candidates, consider candidate regular files in ascending unsigned
  UTF-8 order of canonical path, the same order used for successful modules. Inspect no more than RA-04 plus one actual octet for any one candidate
  and no more than RA-05 plus one actual octet in aggregate. After an
  individual RA-04 cutoff, its unread suffix is excluded and classification
  continues with later canonical identities only while the aggregate horizon
  remains. Validate and normalize every complete content sequence inside this
  horizon. An established content failure wins over established RA facts;
  simultaneous RA facts use ascending ID. The unread suffix after RA-04 and
  every datum after the RA-05 aggregate cutoff are outside the horizon and are
  not examined merely to seek a higher category.
. *Complete-set horizon:* when the raw-content horizon completes without a raw
  cutoff, all candidate content is bounded and available. Establish content
  failures, RA-07 through RA-09, the no-module condition, and finally the
  complete sorted admitted set in that order and under
  <<outcome-precedence>>.

RA-10 or RA-11 may close the active horizon when its contractual interval is
above threshold. No later datum is inspected merely to seek a category that
would otherwise have higher semantic precedence. Facts outside a closed
horizon are not established facts and cannot compete. Facts fully established
inside the same completed horizon still use <<outcome-precedence>>. This makes
the visible result finite and stable for every permutation of equivalent
provider records while allowing duration limits to measure actual elapsed
contract time.

A `fail` is terminal for the whole attempt. It produces no admitted-module set.
A `skip` excludes only that entry. An `admit` adds exactly one module unless
another row causes a whole-attempt failure. The first limit discovered in
provider order is not automatically the winner; only the horizons and
<<outcome-precedence>> select the result.

The total module order is ascending lexicographic order of the unsigned UTF-8
octets of canonical module identity. If one identity is an exact byte prefix
of another, the shorter identity sorts first. This ordering uses no provider
response order, traversal order, filesystem behavior, or locale. Reordering
raw entries therefore cannot change a successful admitted set or order, and
cannot change a collision into a winner.

[[measurement-stages]]
== M1-LIM-0: Measurement stages and boundary rule

The limit inventory is closed: no configurable, inferred, provider-declared,
or implementation-specific product limit can change the M1 outcome. These are
proposed M1 product ceilings, not claims about a chosen technology's capacity,
and no value is copied or inferred from Code City v1. Equal numeric values in
different rows remain separate limits because their data, counting bases, or
measurement stages differ; no threshold is implicitly shared. Related
admission and processing ceilings are intentionally unequal where the same
immutable datum crosses stages, so every named category has a reachable
boundary.

The conceptual stages are:

Retrieval:: Begins when obtaining repository entry data for the already
selected commit begins. It ends when the last repository datum required to
decide admission is available, or when retrieval reaches a terminal outcome.
It includes elapsed waiting for that data and excludes URL/revision resolution.

Admission:: Begins when the first retrieved entry is evaluated. It ends when
the complete normalized, collision-free, ordered admitted set is decided, or
when admission reaches a terminal outcome. Retrieval and admission intervals
may overlap; their limits remain independent.

Static processing:: Begins when the ordered admitted set is presented for the
fixed M1 processing result. It ends when the complete result, or a terminal
processing outcome, is established.

City construction:: Begins when the complete fixed processing result is
available for city construction. It ends when the complete
renderer-independent city/scene model, or a terminal construction outcome, is
established.

Presentation:: Begins when the complete renderer-independent model is
available for initial presentation. It ends when the complete initial
presentation is ready for atomic publication, or a terminal presentation
outcome is established.

Every threshold is an inclusive maximum. A value immediately below or exactly
at the threshold is allowed; merely reaching the threshold is not a failure.
A value exceeds the threshold only when it is greater than the stated value.
Counts and byte sizes are exact non-negative integers. Duration is elapsed time
rounded up to a whole millisecond; zero elapsed time is zero, completion at the
exact threshold is allowed, and any positive fraction beyond it is counted as
the next millisecond and fails. Coordinate accounting is defined with the axis
rows below.

A stage may stop only at a terminal bounded horizon defined in
<<admission-composition>>, or when its own duration becomes terminal. Merely
encountering the first excess in provider response order is not permission to
choose that category. No stop publishes a partial result, and this rule assigns
no stopping mechanism or owner.

|RA-02

|`1,024 UTF-8 bytes per path`

|Path-segment depth
|`64 segments per path`
|Count the non-empty canonical segments separated by `/`; a root-level file has

|One repository entry's content size
|`4,194,304 raw bytes`

|`52,428,800 raw bytes`

|Admitted-module count
|`4,000 modules`
|Count each unique regular candidate with valid normalized content once after
admission and before sorting. Skipped entries are excluded. Distinct identities
with identical content count separately; collisions admit none.

|RA-08
|Normalized content size per admitted module
|`2,097,152 UTF-8 bytes`
|Count the UTF-8 octets of one module after BOM removal and newline
normalization. Raw bytes, module identity, and later processing data are
excluded. Each module is measured once even if its data is later consumed more
than once.

|RA-09
|Aggregate normalized admitted-content size
|`41,943,040 UTF-8 bytes`
|Sum RA-08 for every admitted identity once after normalization and before
static processing. Equal or shared text under distinct identities contributes
once per identity; repeated consumption contributes nothing further.

|RA-10
|Retrieval duration
|`60,000 milliseconds`
|Measure the Retrieval interval defined in M1-LIM-0, including waits and all
entry/content data needed for admission. Exclude URL validation, immutable
revision resolution, later admission-only work, and user time outside the
interval.

|RA-11
|Admission duration
|`10,000 milliseconds`
|Measure the Admission interval defined in M1-LIM-0, including path/content
normalization, collision evaluation, limit accounting, no-module decision, and
deterministic ordering. Exclude earlier URL/revision resolution and later
static processing. Overlap with retrieval is included independently in both
contractual intervals.
|===

|CC-01
|Building count
|`2,000 buildings`

[[limit-reachability]]
== Reachability of related limits

The same admitted identity and normalized content are measured again when they
become static-processing input. Admission normalization never increases raw
content size, and processing receives the complete admitted set without
changing its identities or source octets. The ceilings therefore form these
strict, intentional envelopes rather than equal-threshold conflicts:

[cols="3,2,2,2",options="header"]
|===
|Related data |Outer repository envelope |Admission envelope |Processing envelope

|Entry/module occurrences
|RA-06: `5,000` candidates
|RA-07: `4,000` admitted modules
|SP-01: `2,000` presented modules

|One module's content
|RA-04: `4,194,304` raw bytes
|RA-08: `2,097,152` normalized bytes
|SP-02: `1,048,576` normalized bytes

|Aggregate content
|RA-05: `52,428,800` raw bytes
|RA-09: `41,943,040` normalized bytes
|SP-03: `20,971,520` normalized bytes
|===

These are separate product limits, not shared safeguards. An upstream Below or
At result permits transition from that stage; it does not promise that the
same larger datum also passes a deliberately smaller downstream ceiling. The
following exact Above witnesses prove the formerly conflicting categories are
independently reachable while every prerequisite limit remains compliant:

[cols="1,6",options="header"]
|===
|Winning limit |Compliant witness for its Above boundary

|RA-02
|One structurally valid one-segment ASCII `.ts` path of exactly `1,025` UTF-8
bytes; depth remains one. Its size is a limit fact, not structural invalidity.

|RA-03
|One structurally valid `.ts` path of exactly `65` short non-empty segments and
fewer than `1,024` UTF-8 bytes.

|RA-04
|`4,194,305` raw bytes made from one leading three-byte UTF-8 BOM followed by
`2,097,151` CRLF pairs. If normalization were reached, it would contain
`2,097,151` bytes, below RA-08.

|RA-07
|`4,001` distinct admitted empty modules: below RA-06 and independent of every
content ceiling.

|RA-08
|One valid ASCII module of `2,097,153` bytes: below RA-04 and with aggregate
content below RA-09.

|RA-09
|Twenty modules of `2,097,152` normalized bytes plus one one-byte module:
`41,943,041` bytes in aggregate, with every module at or below RA-08 and raw
aggregate content below RA-05.

|SP-01
|`2,001` distinct admitted empty modules: below RA-07, then above SP-01 when the
complete set is presented.

|SP-02
|One admitted ASCII module of `1,048,577` normalized bytes: below RA-08, then
above SP-02 when consumed.

|SP-03
|Twenty presented modules of `1,048,576` bytes plus one one-byte module:
`20,971,521` bytes in aggregate, with every module at or below SP-02 and the
aggregate below RA-09.
|===

The corresponding At and Below witnesses remove one and two units respectively
from the named Above value while preserving the stated prerequisite
relationships. No downstream architecture or enforcement owner is implied.

[[metadata-policy]]
== M1-LIM-1: Absent and untrusted measurement metadata

Limit compliance is established from the contract data defined in each row,
not from a provider or repository's claimed count, size, duration, encoding,
media type, bound, or completion status.

* An absent, malformed, negative, contradictory, overflowing, or otherwise
  untrusted numeric claim neither proves compliance nor creates a limit
  failure. The actual sequence, octets, text, model, bounds, and elapsed
  interval are measured. A well-formed claim above a threshold is not enough by
  itself to fail, and a claim at or below is never enough to pass.
* Missing or malformed data essential to establish a raw entry inside the
  applicable bounded horizon--its path, kind, or a candidate regular file's
  actual content--is `Source admission failed`. An explicit zero-octet content
  sequence is valid and is distinct from absent content. Contradictory entry
  records and content are admission failures. Data beyond a closed limit
  horizon is intentionally not required and is not reclassified as absent.
* Counts and byte sums are checked no later than the first datum beyond the
  threshold, so arithmetic cannot wrap. If only an overflowing claim is
  supplied and the actual bounded data is unavailable, the data is absent and
  the applicable stage failure is used; the claim is never truncated,
  saturated, or treated as a measured value.
* A repository's symlink-target metadata and content beneath a known submodule
  are not needed for admission and cannot make those skipped entries admissible.
* Static-processing input that is missing, extra, repeated, malformed, or
  inconsistent with the complete admitted set is `Source processing failed`.
  No repository-provided summary may replace the normalized source.
* A label, element, or axis extent that cannot be established as valid Unicode
  text or finite ordered numeric data is `City construction failed`; it is not
  guessed, clamped, or called a limit violation. Presentation data that cannot
  establish a complete initial presentation is `Presentation failed`.
* Durations are measured over the contractual intervals; repository/provider
  timing claims are ignored. If a stage cannot establish its own valid
  completion data, it uses that stage's non-limit failure category and may not
  assume that its duration passed.

These rules and the finite horizons in <<admission-composition>> permit
downstream safeguards to avoid consuming unbounded data. No safeguard may
admit data, change a threshold, expose a partial result, inspect outside a
closed horizon merely to seek another category, or return a different visible
category than this contract and <<outcome-precedence>> require.

[[outcome-precedence]]
== M1-OUT-2: Deterministic precedence

Detection timing, provider response order, and traversal order never select
the visible outcome. First establish facts only inside the finite horizons in
<<admission-composition>> and the completed data of later stages. A cutoff
closes its horizon; an unread suffix, opaque entry field, later canonical
identity, or unfinished later-stage result is not an established competing
fact. Apply this precedence to the established facts for one attempt:

. A newer submission or reload first makes every prior attempt ineligible to
  publish. Its late facts have no result at all.
. For the current Loading attempt, a cancellation invoked before or at the
  same contractual instant as completion or failure wins and produces the
  `Cancelled` state from xref:04-functional-requirements.adoc#states[]. It
  clears the selected identity. If Failure or Success was already stable,
  cancel is unavailable.
. Input, anonymous-access, revision, or resolution outcomes that occur before
  immutable selection use the precedence and categories in
  xref:04-functional-requirements.adoc#failure-outcomes[]; this source contract
  has not started.
. Inside one completed repository/admission horizon, `Source admission failed`
  wins over established RA facts and the no-module condition.
. Simultaneous established RA limit violations use ascending ID order: RA-01
  through RA-11.
. `No supported modules` follows all established source-admission failures and
  RA limits.
. `Source processing failed` wins over established SP limits. Simultaneous SP
  limits use ascending ID order: SP-01 through SP-04.
. `City construction failed` wins over established CC limits. Simultaneous CC
  limits use ascending ID order: CC-01 through CC-09.
. `Presentation failed` wins over established PR-01.
. When facts from different completed stage data are simultaneously available,
  the earlier stage in this list wins: repository/admission, static processing,
  city construction, then presentation.

Consequently, the existence of a `10,001`st opaque record always produces
RA-01 without inspecting record fields for a possible malformed kind or
collision. If RA-01 passes, the bounded path and complete-metadata horizons do
find every structural failure and collision they are required to classify
before content starts. Content classification then uses canonical identity
order and the fixed RA-04/RA-05 horizon, so a malformed suffix or later module
outside that horizon cannot change the category when provider records are
permuted. A higher semantic category already established inside the completed
horizon still wins.

A lower-precedence established fact is not shown as a second category. This
ordering and the cutoff rule are product classification, not an instruction to
perform unsafe extra work or a choice of orchestration mechanism.

[[failure-invariants]]
== M1-OUT-3: Identity retention and no partial or stale result

Every failure on this page occurs after immutable selection. It therefore
retains only the current attempt's canonical repository URL and full lowercase
commit ID in the Failure state. It never shows an identity from a prior
attempt. Cancellation is different: it clears the identity exactly as required
by xref:04-functional-requirements.adoc#states[].

An admission or limit failure publishes no admitted-module set, metric result,
renderer-independent city/scene model, partial city, or stale city. A
non-limit processing, construction, or presentation failure publishes none of
those stage or later results either. Success remains atomic: only the complete
city and its current identity may appear together.

A replacement invalidates the prior city, identity, status, and all partial
work before the new submission is classified. A late admit, metric result,
model, presentation, failure, or limit observation from the replaced or
cancelled attempt has no observable effect and can never make the invalidated
result reappear.
