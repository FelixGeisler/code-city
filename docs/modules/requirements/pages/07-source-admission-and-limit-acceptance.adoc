= Source Admission and Limit Acceptance

These inert documentary scenarios and traceability assignments review
xref:06-source-admission-and-limits.adoc[]. They are not executable fixtures,
test scaffolds, provider stubs, technology choices, or assignments of an
enforcement location.

The contract is acceptable only when all of these gates hold:

* every closed-matrix row has its stated normalization, identity or absence,
  collision result, `admit`/`skip`/`fail` result, and category/code where
  applicable;
* every RA-01 through RA-09 T-1, T, and T+1 example has its stated inclusive
  result with compliant prerequisites;
* permutations and combined facts use the bounded horizons, stable codes, and
  precedence rather than provider response or discovery order;
* replacement, cancellation, failure, late completion, identity retention, and
  atomic publication preserve the accepted #441 invariants;
* CC-01 through CC-08 use only their accepted #444 dispositions; RA-10 and
  RA-11 use only ADR 0006's explicitly-unnecessary disposition and inert
  elapsed-time case; SP-01 through SP-04 use only ADR 0007's
  explicitly-unnecessary full-envelope disposition; and CC-09 and PR-01 use
  only ADR 0008's explicitly-unnecessary disposition and inert elapsed-time
  case; and
* `npm run docs:build` succeeds.

== Admission classification

[source,gherkin]
----
Scenario: Every closed-matrix row has one deterministic admission result
  Given the current attempt selected its canonical repository URL and full commit ID
  And every unmentioned condition is valid and every applicable limit is below its maximum
  When any row in the closed admission matrix is evaluated
  Then its normalization and canonical identity or absence are exactly those stated
  And its collision result is exactly the one stated
  And its only admission result is the row's admit, skip, or fail value
  And any visible result has exactly the row's simple category and stable code
  And no repository metadata, path, or source is executed, evaluated, imported,
      or dynamically loaded
----

[source,gherkin]
----
Scenario: Extension matching is closed and preserves identity
  Given valid regular files use each of ".js", ".jsx", ".mjs", ".cjs",
      ".ts", ".tsx", ".mts", and ".cts"
  And equivalent examples use upper- or mixed-case ASCII suffix letters
  And valid files are also named ".ts" and "name.d.ts"
  And unsupported files include "example.txt" and "example.vue"
  When admission classifies their extensions
  Then every allowed suffix and ASCII case variant is eligible
  And the complete canonical path spelling and case are retained
  And the final segment ".ts" and compound name "name.d.ts" are eligible
  And the unsupported and framework-specific files are skipped
  And no other extension, compound format, Unicode case mapping, or locale rule is inferred
----

[source,gherkin]
----
Scenario: Canonically equivalent paths fail without an order-dependent winner
  Given one entry has NFC path "src/café.ts"
  And another entry has the canonically equivalent decomposed path
  When those entries are supplied in either order
  Then the state is Failure with category "Source admission failed"
  And the governing code is "M1-ADM-1"
  And neither spelling wins or becomes an admitted identity
  And no admitted-module set or city is visible
----

[source,gherkin]
----

  Given one allowed-extension regular file has a structurally valid NFC path
  And only <code> has its exact T+1 value
  When the bounded path horizon classifies the entry
  Then the state is Failure with category "Repository/admission limit exceeded"
  And the governing code is <code>
  And the result is not "Source admission failed"
  And no module identity or admitted-module set is published

  Examples:
    | code  |
    | RA-02 |
    | RA-03 |
----

[source,gherkin]
----
Scenario: Case and prefix peers have a Git-faithful total order
  Given valid modules "src/a.ts" and "src/A.ts" arrive in either order
  And valid modules "a.ts" and "a.tsx" arrive in either order
  When admission completes
  Then every canonical identity retains case
  And "src/A.ts" precedes "src/a.ts" by unsigned UTF-8 octets
  And the shorter prefix identity "a.ts" precedes "a.tsx"
  And provider, traversal, filesystem, and locale order change nothing
----

[source,gherkin]
----
Scenario Outline: No-module results distinguish absence from all-skipped candidates
  Given immutable selection completed for the current attempt
  And <condition>
  And no higher-precedence failure or limit applies
  When admission reaches its terminal result
  Then the state is Failure with category "No supported modules"
  And the governing code is <code>
  And the current canonical repository URL and full commit ID remain visible
  And no admitted set, metric result, city model, partial city, or stale city is visible

  Examples:
    | condition                                                  | code    |
    | no eligible candidate exists                               | ADM-06  |
    | eligible candidates exist but every one is a skipped kind  | ADM-07  |
----

[source,gherkin]
----
Scenario: Malformed syntax remains admitted text
  Given a regular allowed-extension file has a valid canonical path and kind
  And its complete content is valid normalized UTF-8 text
  But its source syntax is malformed
  When admission evaluates the file
  Then the admission result is admit
  And the canonical identity and normalized content join the admitted set
  And admission neither parses nor executes the source
  And no downstream syntax result is selected by this contract
----

The downstream result is defined independently by
xref:08-fixed-metric-semantics.adoc#metric-failure[Atomic metric failure]; this
admission scenario remains an `admit` result.

== Selected-revision completeness and elapsed-time disposition

[source,gherkin]
----
Scenario Outline: Each REST completeness cap is inclusive
  Given a normal readable status-200 CORS response for the <evidence> request
  And every non-size response condition is valid
  When the post-HTTP-content-decoding stream ends at <cap_minus_1>
  Then the body size may continue and creates no separate visible result
  When an otherwise equivalent stream ends at <cap>
  Then the body size may continue and creates no separate visible result
  When an otherwise equivalent stream establishes <cap_plus_1>
  Then the state is Failure with category "Source admission failed"
  And the governing code is "M1-ADM-1"
  And the body is cancelled where feasible and no later request or stage starts
  And none of these transport values is an RA limit or creates another code

  Examples:
    | evidence              | cap_minus_1       | cap               | cap_plus_1         |
    | commit-object body    | 4,194,303 bytes   | 4,194,304 bytes   | byte 4,194,305     |
    | recursive-tree body   | 8,388,607 bytes   | 8,388,608 bytes   | byte 8,388,609     |
----

[source,gherkin]
----
Scenario: A truncated bounded inventory is incomplete
  Given the validated recursive-tree envelope contains at most 10,000 opaque records
  And its own "truncated" value is true
  When selected-revision completeness is classified
  Then the state is Failure with category "Source admission failed"
  And the governing code is "M1-ADM-1"
  And no non-recursive subtree fallback or raw-content request starts

The `10,001`st opaque record remains RA-01 and is not inspected. At most
`10,000` records with `truncated: false` is only potentially complete; every
other envelope, admission, and RA rule still applies.

[source,gherkin]

Scenario: Arbitrary elapsed time is inert while Loading
  Given the current selected-revision attempt is Loading
  And no provider or browser failure occurs
  And the user does not cancel, replace, reload, or otherwise end the attempt
  When arbitrary elapsed time passes
  Then no timer or clock is started for RA-10 or RA-11
  And the state remains Loading

  And M1 makes no completion-time promise

Cancellation, replacement, reload, and provider or browser failure still
follow the accepted state and failure contracts. These are lifecycle outcomes,
not elapsed-time boundaries. There is no timing boundary table and no RA-10 or
RA-11 T-1/T/T+1 scenario.

== Identity, replacement, and atomic publication

[source,gherkin]
----
Scenario Outline: Every admission result retains only the current selected identity
  Given Success previously showed repository A at revision-a
  When a replacement selects repository B at revision-b
  And the replacement reaches <condition>
  Then the state is Failure with category <category>
  And the governing code is <code>
  And only repository B and the full lowercase revision-b identity remain visible
  And repository A, revision-a, every admitted set, metric result, city model,
      partial city, stale city, and presentation are absent

  Examples:
    | condition                         | category                                | code       |
    | no eligible candidate             | No supported modules                    | ADM-06     |

    | canonical path collision          | Source admission failed                 | M1-ADM-1   |
    | missing required kind             | Source admission failed                 | M1-ADM-3   |
    | invalid UTF-8 content              | Source admission failed                 | M1-ADM-4   |

Scenario: A replaced or cancelled attempt cannot publish late data

  Then admitted modules use ascending unsigned-UTF-8 identity order
  And exactly one complete city appears atomically with the current canonical repository URL

[[deferred-evidence]]
== Accepted downstream dispositions and evidence boundaries

RA-10 retrieval duration and RA-11 admission duration are no longer deferred.
They are explicitly unnecessary for M1 and have no value, unit, timer, clock,
category, stable code, precedence, interval, cutoff, boundary, or T-1/T/T+1
scenario. The historical `60,000 ms` and `10,000 ms` proposals remain rejected
as uncalibrated network- and device-dependent outcomes. Controlled mechanism
evidence belongs to https://github.com/FelixGeisler/code-city/issues/454[#454];
integrated and hosted evidence belongs to
https://github.com/FelixGeisler/code-city/issues/460[#460].

SP-01 through SP-04 are no longer deferred. They are explicitly unnecessary
and have no value, unit, timer, clock, cutoff, category, stable code,
precedence, interval, boundary, or T-1/T/T+1 scenario. All `4,000` RA-07
modules, every RA-08-sized module, and all `41,943,040` RA-09 normalized bytes
reach analysis. The historical `2,000` modules, `1 MiB`, `20 MiB`, and `30
seconds` proposals are rejected. Controlled parser/SLOC/unit evidence belongs
to #455, the complete combined rerun to #456, and integrated lifecycle and
renewal evidence to #460.

CC-09 and PR-01 are explicitly unnecessary for M1. They have no value, unit,
timer, clock, deadline, interval, cutoff, category, stable code, precedence,
threshold, boundary, or T-1/T/T+1 scenario. Elapsed construction or
presentation time alone leaves the attempt `Loading` and creates no outcome.
xref:architecture:adr/0008-browser-native-webgl2-instanced-city-presentation.adoc[ADR
0008] records the fixed-envelope feasibility basis and #451's accepted
decision.

CC-01 through CC-08 are no longer deferred. Their only accepted dispositions
are the exact table in
xref:06-source-admission-and-limits.adoc#deferred-limits[] and the authoritative
city contract in xref:10-fixed-city-layout-and-presentation.adoc#city-limit-dispositions[]:
exactly `N` buildings and `N` scene prisms, zero labels, no applicable label
bytes, no independent city or coordinate caps, exact derived bounds, and no
independent limit-exceeded outcome. Missing, additional, or repeated mappings
remain `M1-CITY-1`; private capacity remains a conformance defect.

https://github.com/FelixGeisler/code-city/issues/457[#457] owns focused CC,
construction, and `M1-CITY-1` evidence;
https://github.com/FelixGeisler/code-city/issues/458[#458] owns complete fixed
WebGL presentation, defensive handoff, drawing-buffer, staging, resize,
context-loss, cleanup, and absence evidence; and
https://github.com/FelixGeisler/code-city/issues/460[#460] retains integrated
and hosted state and lifecycle evidence. The hard gate in
https://github.com/FelixGeisler/code-city/issues/464[#464] verifies the recorded
human delegation, its #444, #450, and #451 exercises, accepted ADRs 0007 and 0008,
and the exact evidence ownership before M1 implementation handoff. No
downstream issue body is changed by this documentation allocation.
